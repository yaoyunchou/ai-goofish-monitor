# 店铺商品采集预算与「保量 + 补位」选品算法

> 状态：**设计定稿 v4（2026-09-18 全部澄清完成，可开工）** · 关联：[`item-monitor-health.md`](./item-monitor-health.md)
> 本文是「每店最多采 100 个，不达标的踢掉、用没采过的补上」这一需求的 **算法 SSOT**

## 0. 最终确认的规则

### 0.1 你的原话（三次澄清 + 两次决策）

> **v1**：「保证有浏览量，但是最近的浏览量也要有增长。每个店铺应该有很多商品，但是每次采集最多 100 个，有商品不满足条件则需要再找几个来补充采集的数量，同时补充的商品是**没有参加过采集**的，**就算以前是被筛选掉的也算被采集过**。不断的按规则进行筛选，看到最后剩下的采集数据。」
>
> **v2**：「1. 计算浏览量。2. A 店铺有 300 个商品，我采集了 100 个，一周后我发现这 100 个里有 30 个浏览增量小于 20，那这 30 个被标记为不采集了，我会再从 300 个里面找**没有被采集过的**，进行**商品 ID 对比**，如果在采集商品里面了就不加到采集表里。做法就是给一个店铺添加新采集商品，满足**从来没有采集过**则补充到该店铺的采集列表，不满足就不加入。3. 就是从**在售商品**里去找满足条件的，**没有什么优先顺序**。」
>
> **决策 1（阈值）**：「增量阈值是 **20**」→ `MONITOR_KEEP_VIEW_GROWTH=20`
>
> **决策 2（路线）**：「**路线 A**：席位置空就置空，不为凑数采烂商品」→ `SELECTION_ROUTE=A`

## 1. 心智模型：逐步收敛

```
第 0 周：在售 300 个 → 选 100 个 → 采集
                            ↓
第 1 周：100 个里 30 个浏览增量 < 20 → 标记不采集
        从「300 个里没采过的 200 个」中取 30 个补上（ID 对比）→ 又是 100 个
                            ↓
第 2 周：再踢、再补 …… fresh 池以「每次补位数量」的速度消耗
                            ↓
第 7 周左右：200 个 fresh 用完 → 席位开始空出来 → 收敛
                            ↓
稳态（路线 A）：该店所有"值得采"的商品都在监控中，**席位可能不满 100 —— 空着就空着**
```

**模型性质**：
- 每个商品**最多被采一轮** → 绝不反复抓同一条废弃商品，配额利用率最高
- **天然收敛** → 不需要熔断、冷却、防抖参数
- **路线 A = 不补烂货** → 席位不满是**预期结果**，不是故障；监控里的就是真精选
- **席位不满 100 是正常终态**，不是 bug —— 正是你说的「看到最后剩下的采集数据」

## 2. ⚠️ 数学推演：多久枯竭（用你的 300 例子）

按你的例子精确推演（在售 300、席位 100、踢出率 30%）：

| 周 | 在监控 | fresh 可用 | 空席 |
|----|--------|-----------|------|
| 0 | 100 | 200 | 0 |
| 1 | 100 | 170 | 0 |
| 2 | 100 | 140 | 0 |
| 3 | 100 | 110 | 0 |
| 4 | 100 | 80 | 0 |
| 5 | 100 | 50 | 0 |
| 6 | 100 | 20 | 0 |
| **7** | **90** | **0** | **10** |
| 8 | 63 | 0 | 37 |
| 9 | 45 | 0 | 55 |
| 10 | 32 | 0 | 68 |

**`fresh` 在第 7 周耗尽。之后席位按踢出率指数衰减。**

**根因**：`fresh` 总量是**固定**的（= 在售总数 − 已采数），但每周消耗量 = 踢出数。二者相遇的时刻 = `fresh ÷ 每周踢出量`。

```
耗尽周数 ≈ fresh池大小 ÷ (席位数 × 踢出率)
        = 200 ÷ (100 × 0.30)
        = 6.7 周
```

> **两种口径都对，只是问法不同**：
> - 逐周递推表（上表）→ **第 7 周**开始出现空席
> - 解析式向下取整 `int(200 / 30)` → **6 周**（还能**补满**的完整周数）
>
> 模拟脚本 B0 用解析式，报告里看到 `6 周` 就对应上表的「第 7 周掉下来」。

**这个公式很重要**，它说明：

| 店铺在售总数 | 踢出率 10% | 踢出率 20% | 踢出率 30% |
|-------------|-----------|-----------|-----------|
| 200 | 10 周 | 5 周 | 3 周 |
| 300 | 20 周 | 10 周 | **7 周** |
| 500 | 40 周 | 20 周 | 13 周 |
| 1000 | 90 周 | 45 周 | 30 周 |

**结论**：
- 你例子里这个 300 商品的店，**7 周后就没有新商品可补了**
- 只有「在售数 ≫ 席位数」且「踢出率低」的店才能长期维持 100 席
- **这不是算法问题，是规则本身的结构性质** ── `fresh` 是**有限的一次性资源**

### 2.1 ⚠️ 阈值 10 vs 20 的敏感度（你已选 20）

踢出率**不是常数**，它由阈值决定。阈值越严 → 踢得越多 → 枯竭越快：

| 增量阈值 | 典型踢出率 | 300 商品店的枯竭周数 | 一年内 |
|---------|-----------|-------------------|--------|
| `view_growth ≥ 10` | ~15% | 约 13 周 | ❌ |
| **`view_growth ≥ 20`（已定）** | **~30%** | **约 6 周** | ❌ |

> **这不是估算，是必须实测的**。上表的踢出率是占位值；
> 真实数字必须跑 B0 拿到（见 §5）。跑之前先假定「**会比你想的快**」。
>
> 选了 20 意味着：**约 1.5 个月后，这个店就基本只有真正头部的商品留在监控里了**。
> 这符合你的目标（"看最后剩下的"），但要有心理预期 —— 席位会从 100 掉到几十。

## 3. 枯竭之后怎么办？→ **已定：路线 A**

决策 2 已确认走**路线 A**。下面是三条路线的完整对照，保留供日后参考。

### ✅ 路线 A：席位置空，不为凑数采烂商品（**已采纳**）

- `fresh` 用完 → 席位自然降到稳态（可能只剩 30~50 个）
- **这恰恰是你说的「看到最后剩下的采集数据」** —— 剩下的就是这家店真正值得盯的商品
- **优点**：配额利用率最高，绝不浪费；实现最简单（什么都不用做）
- **代价**：不再"每店 100 个"

**实现要点**：
```python
# 只补到 need 个；fresh 不够就有多少补多少，剩下的席位空着
backfill = fresh[:need]           # 关键：不做「为凑满而降低门槛」
```

**绝不要做的事**（路线 A 的红线）：
- ❌ 为了凑满 100 席，把被踢的重新拉回来
- ❌ 为了凑满 100 席，降低 `MIN_VIEW_TOTAL` / `KEEP_VIEW_GROWTH`
- ❌ 为了凑满 100 席，补 `view_end = 0` 的僵尸商品
- ✅ 席位空着就空着 —— **空席本身就是"这个店没有更多好货"的信号**

### 路线 B：给踢出的商品加"复活期"，到期重新参与补位（**未采纳**）

- 被踢出的商品**满 N 周（如 8 周）后可重新进入补位池**
- **优点**：席位能长期维持 100
- **代价**：**违反 R4「被采集过就不再加入」** —— 但这是唯一能长期维持 100 席的办法
- **注意**：不等于反复采烂商品，因为有 8 周间隔，且可限制「同一商品最多复活 1 次」

### 路线 C：只让「存量达标、仅增量差」的复活（**未采纳，备选**）

- 存量过线（`view_total ≥ 100`）但本周增量不行的 → 复活（可能只是这周没动）
- 存量本身就不行的 → 永久出局（真没希望）
- **优点**：精准，不浪费在真冷门
- **代价**：逻辑稍复杂，但比 B 更符合你的本意

> **保留 C 作为退路**：跑 B0 后若发现席位掉得比预期狠（比如 3 个月内掉到 30 以下），
> 可以只针对「存量达标、仅增量差」的那部分启用回炉 —— 既救回席位，又不违你的本意。

## 4. 实现方案

### 4.1 判定函数（双门槛 AND）

```python
def evaluate_item(row, *, min_view_total, min_view_growth, min_want_growth):
    """存量 + 增量 两个门槛都要过。"""
    view_total  = row["view_end"]      # 累计浏览量（R1 口径 = 计算浏览量）
    view_growth = row["view_growth"]
    want_growth = row["want_growth"]

    passed_stock  = view_total >= min_view_total                    # R1
    passed_growth = (view_growth >= min_view_growth                 # R2
                     or want_growth >= min_want_growth)
    return passed_stock and passed_growth
```

**默认阈值（已定稿）**：

```env
MONITOR_MIN_VIEW_TOTAL=100      # R1：累计浏览量下限（保证有浏览量）
MONITOR_KEEP_VIEW_GROWTH=20     # R2-A：周浏览增长下限 ← 决策 1 已定为 20
MONITOR_KEEP_WANT_GROWTH=2      # R2-B：周想要增长下限（替代通道）
SELECTION_ROUTE=A               # 决策 2：席位置空，不补烂货
SELECTION_ENABLED=false         # 总开关，默认关（先 dry_run 观察）
```

> ✅ 阈值 20 已确认（曾与 10 冲突，现按你最后的说法定 20）。
> 效果：比 10 **踢得更狠**，好处是收敛更快、留下的更精；代价是席位掉得更快。见 §2.1。

### 4.2 补位算法（R4/R5/R6 的实现）

```python
# 1. 取该店在售商品（必须放大 max_items，否则只看得到前 100）
items = [i for i in profile["卖家发布的商品列表"] if i["商品状态"] == "在售"]

# 2. 读该店「已采集过」的 item_id 集合（= seller_subscription_items 全表，含被踢出的）
captured_ids = load_captured_item_ids_sync(seller_user_id)

# 3. 分裂
known    = [i for i in items if item_id_of(i) in captured_ids]      # 采过 → 参与判定
fresh    = [i for i in items if item_id_of(i) not in captured_ids]  # 没采过 → 补位来源

# 4. known 里达标的保留，不达标的踢出
active = [i for i in known if evaluate_item(...)]
kicked = [i for i in known if not evaluate_item(...)]

# 5. 补位：需要几个就从 fresh 取几个（无优先顺序，R6）
need     = item_limit - len(active)
backfill = fresh[:need]        # 按在售列表顺序

# 6. 本轮采集列表 = active + backfill
#    ⚠️ 路线 A：len(backfill) < need 时，余下的席位【空着】，不降门槛去凑
```

**"商品 ID 对比"就是第 3 步** —— `captured_ids` 用 `seller_subscription_items` 做集合判定，一次查询，无需逐条比对。

**路线 A 的第 6 步是重点**：`need` 是"最多要几个"，不是"必须凑满几个"。
`fresh` 不够时，`len(active) + len(backfill)` 就是该店当前的真实上限。

### 4.3 前提改造：`max_items` 必须放大 ⚠️

**这是 R4 能否成立的关键。** 现状 `src/seller_subscription_scraper.py:208-221`：

```python
profile = await scrape_user_profile(..., max_items=item_limit)  # 只抓前 100 条
items = [i for i in profile["卖家发布的商品列表"] if ...][:item_limit]
```

**问题**：你的店有 300 个商品，但代码只抓前 100 条 → **第 101~300 名永远进不了 `fresh` 池** → 补位无货可补。

**必须改为**：

```python
profile = await scrape_user_profile(..., max_items=CANDIDATE_POOL_MAX)  # 如 500 或 None（全量）
items = [i for i in profile["卖家发布的商品列表"] if i["商品状态"] == "在售"]
# 不再 [:item_limit] 截断！
```

| 选项 | 优点 | 缺点 |
|------|------|------|
| `max_items=None`（全量） | 一次看全，补位永远有货 | 滚动页数多 → **风控暴露面大** |
| `max_items=500` | 平衡 | 超大店仍看不全 |
| `max_items=item_limit × 3` | 保守 | 300 商品的店刚好覆盖 |

> **成本优势**：主页列表是**滚动翻页**（1 页 20~30 条 / 1 次请求），详情是**每商品 1 次请求**。
> 把预算从"多采详情"挪到"多翻几页主页"**便宜得多**。
> **风险**：滚动轮数增加 → 触发风控。建议先 `item_limit × 3`（300 商品的店正好全覆盖），观察后调。
