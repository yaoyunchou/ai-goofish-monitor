# 商品监控健康度与自动停用 · PRD

> **交付状态**：**已交付（默认安全空跑）** · `MONITOR_AUTO_DISABLE_ENABLED=false`、`MONITOR_DRY_RUN=true`
> **提出日期**：2026-09-18 · 对应设计：[`docs/design/item-monitor-health.md`](../design/item-monitor-health.md)
> **归档**：[`milestone-2026-09-20.md`](./milestone-2026-09-20.md)；默认改为真正自动停用须用户改 env，不在本期默认行为

## 1. 问题

卖家订阅跑久了以后，很多商品的浏览量和想要数一周都不怎么动。它们继续占着每轮采集配额，等于把有限的采集能力浪费在死商品上。

人工逐条看商品列表、判断"这个还要不要继续盯"，成本高且容易漏。

## 2. 目标用户与场景

**用户**：长期运行卖家订阅、订阅了多个卖家（几十~几百个商品）的运营者。

**场景**：每周一次，系统自动回顾上周所有订阅商品的表现，把「浏览和想要都低、也没有增长」的挑出来停止监控，让采集配额集中到有价值的商品上。

## 3. 需求

### 3.1 核心需求（本期交付）

| # | 需求 | 验收标准 |
|---|------|----------|
| R1 | 以**固定自然周**（周一~周日，Asia/Shanghai）为判定周期 | 每周一 09:00 自动跑一次，判定上一完整周 |
| R2 | 判定指标为**浏览量 + 想要数**的周增量 | 达标准确；周内仅 1 天数据的商品不参与判定 |
| R3 | 保留条件用 **OR**：浏览增长达标 **或** 想要增长达标 | 默认浏览 ≥ 10 或想要 ≥ 2 即保留 |
| R4 | 两者都不达标 → **停止监控该商品** | 商品不再进入后续采集范围 |
| R5 | **按单个商品**粒度停用，不影响同卖家的其他商品 | 同卖家其他商品照常采集 |
| R6 | 停用后**发送通知**（复用现有通知渠道） | 通知含停用数量与商品清单 |
| R7 | 支持**手动恢复**单个商品的监控 | 提供恢复接口，恢复后下一轮即重新采集 |
| R8 | **不删除任何数据** | 停用后 `seller_item_daily_metrics` 历史行数不变 |

### 3.2 安全需求（强制）

| # | 需求 | 原因 |
|---|------|------|
| S1 | 默认 **不启用**（`MONITOR_AUTO_DISABLE_ENABLED=false`） | 阈值未经真实数据验证前不能自动动生产数据 |
| S2 | 默认 **空跑**（`MONITOR_DRY_RUN=true`），判定结果照常落库 | 先观察、再启用 |
| S3 | 新品保护期（默认 14 天）内不判定 | 新收录商品数据量天然不足 |
| S4 | 周内有数据天数不足（默认 < 2）不判定 | 数据不足不能下结论 |
| S5 | 数据中途中断的商品 **不停用** | 商品可能已售出退出采集范围，「没数据」≠「不健康」——这条最重要 |
| S6 | 可设每周停用上限（`MONITOR_MAX_MUTE_PER_WEEK`） | 防误判导致批量停产 |
| S7 | 采集侧读取停用集合失败时 **降级为不过滤** | 数据库抖动不能让采集任务崩 |
| S8 | 提供**只读体检脚本**用于阈值校准 | 上线前必须能看清真实数据分布 |

### 3.3 非目标（本期不做）

- 不做可视化看板 / 趋势图表（用户明确要求先做自动停用）
- 不做阈值自适应 / 机器学习
- 不做「停用后自动复活探针」
- 不改动关键词任务的启停逻辑
- 不新增前端页面（仅后端接口 + 文档）

## 4. 关键决策记录

| 决策 | 选择 | 备选 | 理由 |
|------|------|------|------|
| 判定指标 | 浏览 + 想要 | 仅浏览 / 仅想要 | 用户明确指定这两个指标 |
| 保留逻辑 | OR | AND | 用户明确选择：任一达标就保留，避免误杀 |
| 周期 | 固定自然周 | 滚动 7 天 | 用户明确选择；周期边界清晰，便于复盘 |
| 粒度 | 按商品 | 按卖家 | 用户明确选择；卖家整体好坏不代表单个商品好坏 |
| 优先级 | 先数据体检 | 先建看板 | 用户明确选择；先看清数据再定阈值 |
| 停用实现 | 新增 `is_muted` 列 | 复用 `item_status` | `item_status` 是闲鱼侧「在售」状态，语义不同，复用会互相污染 |
| 落库策略 | 保留与停用**都**记录 | 只记停用 | 空跑期必须能观察「本该保留的」判定是否正确 |

## 5. 验收清单

- [x] 自然周计算正确（周一~周日，跨月/跨年正确）
- [x] OR 逻辑正确（含边界：浏览 == 10 保留、想要 == 2 保留、9 + 1 停用）
- [x] 数据不足 / 新品保护 / 缺指标 / 数据中断 均不触发停用
- [x] 默认配置下（关闭 + 空跑）**不产生任何实际停用**
- [x] 停用后历史日指标行数不变
- [x] 停用商品不再进入采集范围，且不影响同卖家其他商品
- [x] 读取停用集合失败时采集正常继续
- [x] `GET /items/health` 不被 `/items/{item_id}/detail` 路由吞掉
- [x] 手动触发接口可用（`dry_run` 可覆盖）
- [x] 恢复接口可用
- [x] 只读体检脚本可运行且**不改数据**

## 6. 上线路径

见 [`docs/design/item-monitor-health.md` §9](../design/item-monitor-health.md)。要点：**先体检校准阈值 → 空跑观察 1~3 周 → 确认无误后再开总开关**。
