# PRD：多渠道并行执行（增量）

> **交付状态**：本期实现  
> **提出日期**：2026-09-23  
> **类型**：简单增量 PRD（无竞品分析）  
> **对应设计**：`docs/design/channel-execution.md`

## 1. 项目信息

| 项 | 内容 |
|----|------|
| 项目 | `ai_goofish_monitor`（闲鱼智能监控） |
| 语言 | 中文 |
| 后端 | Python / FastAPI |
| 前端 | Vue 3 + Vite（非 React） |
| 变更性质 | 调度与执行规范增量；不改各渠道采集业务逻辑本身 |

### 1.1 原始需求复述

闲鱼侧因平台风控，同一时刻不能跑两个闲鱼任务（浏览器 / 登录态资源互斥）。小红书与闲鱼不是同一套爬虫：闲鱼走 `spider_v2.py` + Playwright + 登录态；小红书用另一个浏览器打开公开页，不带登录态。因此不同渠道应当同时执行、互相不等待。该规则要做成可复用规范，后续新渠道按同一套方式接入，而不是在调度代码里继续堆判断。

## 2. 产品定义

### 2.1 目标

1. **同渠道串行**：同一渠道内任务排队，避免闲鱼双开浏览器触发风控。
2. **跨渠道并行**：闲鱼忙时，小红书采集仍可立即开始；反之亦然，互不堵调度。
3. **可扩展接入**：新渠道通过统一「渠道定义 + 执行线」接入；接入步骤写在设计文档，不散落在调度判断里。

### 2.2 用户故事

1. 作为运营者，我希望闲鱼关键词或卖家订阅跑着的时候仍能启动小红书公开采集，这样两套互不相关的爬虫不会互相耽误。
2. 作为运营者，我希望系统保证同一时刻只有一个闲鱼任务在开浏览器，以降低闲鱼风控风险。
3. 作为运营者，我希望手动再点启动且该渠道正忙时立刻得到提示，这样请求不会挂到整轮采集结束才返回。
4. 作为开发者，我希望新渠道按固定步骤注册执行线与排队规则，而不必改一堆散落的调度分支。
5. 作为运营者，我希望界面只在现有入口提示「该渠道正在采集」，不增加新菜单也能理解为何启动失败。

## 3. 渠道定义

一条渠道等于一套爬虫资源（进程模型、浏览器或 HTTP、登录态、互斥范围）。调度按渠道排队与并行，不按业务菜单，也不按闲鱼账号拆线。

### 3.1 本期渠道

| 渠道 ID | 爬虫资源 | 覆盖的业务能力 | 说明 |
|---------|----------|----------------|------|
| `goofish` | `spider_v2.py` + Playwright + 登录态 | 关键词任务、卖家订阅、店铺罗盘 | 同一渠道，共享一条执行线；同渠道内排队 |
| `xhs` | 公开页浏览器渲染（不带登录态） | 公开商品采集 | 独立执行线；与 `goofish` 并行 |

### 3.2 明确不算渠道

| 能力 | 原因 |
|------|------|
| 健康度周判定 | 只查库做判定，不占用爬虫资源；不注册为渠道，不参与渠道排队 |

## 4. 需求池

### P0（必须本期）

| # | 需求 | 说明 |
|---|------|------|
| P0-1 | 两条执行线与排队规则 | `goofish` 与 `xhs` 各一条执行线；同渠道排队，跨渠道并行 |
| P0-2 | 新渠道接入步骤写进设计 | 注册渠道 ID、绑定爬虫资源、声明执行线；禁止在调度代码里散落渠道特判 |

同渠道已有任务在跑时，后续定时触发进入该渠道队列。跨渠道时，任一渠道忙碌不影响另一渠道开跑。健康度周判定不进渠道队列。

### P1（本期尽量）

| # | 需求 | 说明 |
|---|------|------|
| P1-1 | 界面只提示「该渠道正在采集」 | 无新菜单、无新页面；手动启动失败时沿用现有 toast / 接口错误 |

### P2（可延后）

| # | 需求 | 说明 |
|---|------|------|
| P2-1 | 渠道队列可视化 | 非本期 |
| P2-2 | 第三个渠道落地 | 本轮只定规范，不实现第三个渠道 |
| P2-3 | 按闲鱼账号拆多条执行线 | 明确非目标 |

## 5. 验收标准

| # | 场景 | 期望 |
|---|------|------|
| A1 | 闲鱼任务（关键词 / 卖家订阅 / 店铺罗盘任一）进行中 | 小红书公开采集仍能开始 |
| A2 | 已有一个闲鱼任务在跑，再触发另一个闲鱼任务 | 不会同时开两个浏览器；定时后到者排队，手动后到者立刻拒绝 |
| A3 | 小红书采集进行中 | 不会堵住闲鱼侧的调度与开跑 |
| A4 | 定时触发且该渠道正忙 | 任务入队，不丢这一枪 |
| A5 | 手动再点且该渠道正忙 | 立刻返回忙线提示；请求不挂到整轮结束 |
| A6 | 手动启动失败 | 前端无新页面；沿用现有 toast / 接口错误提示 |

## 6. 默认行为

| 触发方式 | 该渠道空闲 | 该渠道正忙 |
|----------|------------|------------|
| 定时（Cron） | 立即执行 | 入队，保留这一次触发，不丢枪 |
| 手动 | 立即执行 | 立刻返回「该渠道正在采集」；不阻塞请求至整轮结束 |

跨渠道：对方渠道忙闲与本渠道无关。

## 7. UI

没有新页面、没有新菜单。手动启动失败时沿用现有 toast / 接口错误，文案体现「该渠道正在采集」。

## 8. 非目标

- 不按闲鱼账号拆执行线。多账号仍共享 `goofish` 一条线。
- 不把小红书改成走 `spider_v2.py` / Playwright。
- 不改各渠道现有采集节奏、限速与 Cookie / 登录态策略。
- 不在本轮实现第三个渠道。
- 不把健康度周判定纳入渠道互斥。
- 不改业务采集字段、AI 分析、通知内容等与调度无关的逻辑。

## 9. 待确认问题

| # | 问题 | 默认假设 |
|---|------|----------|
| Q1 | 同渠道定时入队是否合并重复触发？ | 本期 FIFO 入队；同一任务仍由调度器 `max_instances=1` 挡住，不排两遍 |
| Q2 | 店铺罗盘是否走 `goofish`？ | 是，与关键词、卖家订阅同渠道 |
| Q3 | 忙线是否要稳定错误码？ | 可读文案即可，HTTP 409 |
